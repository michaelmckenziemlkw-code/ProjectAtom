# Архитектура 3D-технопробы

Технопроба исследует читаемость модели и анимаций. Это пока не перенос всей игры в 3D: здесь нет оператора, создания матча, общего времени, лечения или финального взрыва. Предыдущая голосовая эстафета остаётся в `game.html`, эталон времени — в `sync-stand.html`. Оба файла сохранены без изменений.

## Карта проекта

```text
index.html                       точка входа браузера
src/
  main.ts                        сборка приложения, события, жизненный цикл
  core/
    observation.ts               наблюдения, варианты признаков, локальные ответы
    motion.ts                    чистые траектории трёх жестов
    observation.test.ts          проверка правил и геометрии движений
  render/
    createStudyScene.ts          движок, камера, свет, тени, качество, освобождение ресурсов
    environment.ts              почва, корни, растения, следы контакта
    meshTools.ts                 вспомогательное построение геометрии
    contactAudio.ts              включаемые звуки удара и скрежета
    models/
      beetle.ts                  контракт заменяемой модели
      proceduralBeetle.ts        первая модель и её сочленённые лапы
  ui/studyView.ts                 DOM, формы и сообщения
  style.css                      оформление и адаптивная компоновка
tests/browser/study.spec.ts       проверка собранного приложения с настоящим WebGL
public/                          поставляемые локально ресурсы
dist/                            результат сборки, не хранится в Git
```

Зависимости направлены от представления к правилам: `core` не импортирует Babylon.js или DOM. `main.ts` связывает состояние наблюдения с интерфейсом и сценой. Модель не знает, как игрок ответил на вопрос. Справочник и будущие эстафеты не должны обращаться к конкретным мешам или суставам.

## Модель и анимации

`BeetleFactory` создаёт `BeetleActor`. У него есть корневой узел, `present({ gesture, symbol, seconds })` и `dispose()`. Фабрика передаётся в асинхронную `createStudyScene`; она может сразу вернуть актёра или вернуть Promise для загрузки GLB. По умолчанию используется процедурная модель. Это точка замены модели, а не универсальная система персонажей.

Сейчас тело, панцирь, глаза, усики, брюшная пластина, знаки и шесть сочленённых лап строятся из геометрии Babylon.js. Траектория активной лапы задаётся в `core/motion.ts`, а модель превращает её в положение сегментов. Это постановочная анимация с меняющейся длиной сегментов, не полноценная биомеханическая симуляция или готовый скелетный риг.

Три жеста имеют разные признаки:

- `wave`: лапа всё время над поверхностью; нет контакта, пыли и звука удара.
- `tap`: два коротких контакта в одном месте и пауза; есть отдельные звуковые импульсы.
- `scrape`: длительный контакт с перемещением вдоль земли; растут борозды и звучит скрежет.

Пауза останавливает локальное время жеста и звук. В скрытой вкладке время жеста также не продвигается. Это политика самостоятельной технопробы; она не определяет будущую политику общего таймера матча. Камеру можно вращать и во время паузы.

## Как позднее добавить модель из Blender

1. Хранить исходный `.blend` отдельно от готовой сборки, например в `art/source/`, экспортировать GLB в `public/models/`.
2. Согласовать масштаб (одна единица — один метр), землю `Y=0` и перед персонажа вдоль `-Z`.
3. Подготовить скелет и клипы `idle`, `wave`, `tap`, `scrape`. Знак на брюшке должен быть отдельной заменяемой деталью или материалом.
4. Добавить Babylon glTF loader и отдельную фабрику `createGlbBeetle`. Она загрузит модель, реализует тот же `BeetleActor` и сопоставит названия клипов с `gesture`, а `seconds` — с временем воспроизведения.
5. Передать новую фабрику в `createStudyScene`. Правила распознавания и UI не менять.
6. Сверить моменты контакта анимационных клипов с пылью и звуком. Для клипов другой длительности нужно также обновить временные метки контакта; одной замены файла недостаточно.

Загрузчика GLB и демонстрационной модели из Blender сейчас нет: контракт подготовлен, фактический импорт проверяется при появлении первого такого ресурса. Все нынешние модели созданы программно внутри проекта; сторонние модели и внешние текстуры не используются.

## Контент и будущая игра

`createObservations(seed)` воспроизводимо задаёт три наблюдения: каждый жест встречается один раз, порядок и знаки меняются. Число в параметре URL `?seed=12` удобно для повторной проверки. Это локальный сид технопробы, не пакет матча ATOM1 и не обещание совместимости генераторов.

Обычный HUD не называет текущий жест. Игрок может выбрать описание для проверки; правильность появляется только после ответа. Варианты ответа скрыты в details. Подсказки открываются только по запросу и расходуют общий HintBank. Бесплатного описания в настройках нет.

При переносе эстафеты из `game.html` её состояния и переходы следует вынести в отдельный модуль `core/relay`, а сгенерированные соответствия — в данные контента. Обе роли останутся в одном приложении. Действия партнёра передаются голосом и последующим вводом; состояние мира не синхронизируется через физический движок, сеть или общий localStorage.

Не вводим заранее сетевой сервер, сложную ECS, универсальный редактор квестов или глобальную шину событий. Новую эстафету сначала выражаем небольшим набором состояний и действий; обобщаем только реально повторившиеся части.

## Сборка и поставка

Babylon.js, TypeScript и Vite закреплены в `package-lock.json`. Воспроизводимая установка — `npm ci`; никаких CDN при игре. Движок импортируется отдельными модулями, чтобы не включать весь Babylon.js со всеми подсистемами.

`npm run build` проверяет типы и создаёт `dist/`. Его можно целиком скопировать на другой компьютер и раздавать локальным HTTP-сервером. Это одна сборка приложения с несколькими файлами; открытие `dist/index.html` через `file://` не поддерживается. Публичный сервер не нужен. Локальный сервер только отдаёт файлы.

## Проверка

- `npm run test:unit`: воспроизводимость контента, локальные ответы и физические различия траекторий, включая непрерывность цикла.
- `npm run build`: TypeScript и производственная сборка.
- `npm test`: собранный сайт, реальный WebGL, изменение изображения при движении и стабильность при паузе, камера, звук, подсказки, исправление ответа, отсутствие внешних запросов, узкий экран и потеря видеоконтекста.

Linux Chromium в облаке использует программный рендеринг для тестов. Его результаты не устанавливают производительность на видеокартах Windows/Mac и не доказывают, что человек уверенно различает жесты. Для этого нужен отдельный пользовательский прогон.

## Первый пользовательский прогон

1. Сначала оставь звук выключенным, подсказки и проверку ответа закрытыми. Посмотри три наблюдения в общем плане и вблизи.
2. Попробуй описать другому человеку знак и движение без чтения вариантов ответа. Может ли он различить взмах, удар и скребущее движение по твоему рассказу?
3. Затем проверь ответы в интерфейсе. Если ошибся, отметь, что мешало: ракурс, перекрытая лапа, слишком похожая траектория или недостаточно заметный контакт с землёй.
4. Включи звук и сравни впечатление. Он может помогать, но визуальное различие должно работать и без него.
5. Повтори в браузерах Windows/Mac. Если сцена тормозит, проверь уменьшенное качество и зафиксируй браузер и устройство. Облачные тесты не устанавливают целевую частоту кадров.

## Время, графика и помощь (0.8)

`core/timing.ts`: ActiveClock считает всё активное время по performance.now, меняет состояние на событиях входа, паузы и видимости. Смена наблюдения сбрасывает его время. FramePacer допускает только отрисовки с нужным интервалом; после задержки нет серии догоняющих кадров. На 5 FPS цикл жеста сохраняет длительность, но движение становится прерывистым. Звук обновляется независимо от разрешения рисовать. Будущая физика потребует отдельного фиксированного шага; в этой пробе её независимость от FPS не проверяется.

FrameMeter учитывает только выполненные scene.render в основном цикле (прогрев до входа в сцену не включён). Canvas содержит data-animation-time и data-render-count для интеграционных проверок. DOM не ограничен FramePacer, busy-wait нет.

`core/graphics.ts` вычисляет произведение затрат и усилений от замеренной базы X вместо прежней таблицы фиксированных FPS. Реальные коэффициенты модели, источники и ограничения в [design/FPS.md](design/FPS.md). `effectiveFrameCap(settings, baselineFps, cinematicCap = 0)` возвращает 0 для отсутствия искусственного лимита. Ручной и будущий художественный пределы — верхние границы после умножения. `UncappedFpsSampler` принимает только фактические неограниченные отрисовки при активной видимой сцене, фиксирует базу после ≥1,5 секунды и ≥3 интервалов. Скрытие/пауза прерывают незавершённую выборку; ограниченные кадры не снижают базу повторно. Реальная смена качества сцены сбрасывает замер.

`ui/graphicsPanel.ts` управляет настройками без сохранения. `core/hints.ts` хранит общий запас и последовательные уровни событий, не знает о DOM. В пробе одно событие beetle с тремя уровнями и запасом 10: общий намёк, предложение описать необычное партнёру, прямое описание текущего знака и жеста. Прочтение и смена наблюдения не списывают очки; перезагрузка сбрасывает прогресс. Распределение помощи между ролями полной игры ещё не спроектировано.

Графическая панель оформлена как широкое меню с секциями технологий, реконструкции изображения и частоты кадров. Все переключатели технологий — семантические select с вариантами «Выкл.»/«Вкл.», выбор технологии апскейлера включает отдельный select режима. Справа отображаются реальные отрисовки, действующий предел, предпросмотр изменений и контекстное пояснение строки по наведению, фокусу или выбору. На экранах до 750 px колонки становятся одной, панель прокручивается. Клавиатурный выбор и доступные названия сохранены.

Проверка итоговой версии 0.8: npm run test:unit — 11 прошли; npm run build — успешно; полный npm test с системным Chromium — 6 прошли, без пропусков. Снимки обычного экрана и графического меню обновлены и просмотрены. Тест паузы сравнивает изображение самого canvas и активное время, а не пиксели DOM-кнопок. Это проверка Linux/программного WebGL, не замер производительности Windows/Mac.

Последующее уточнение подачи: вкладка «Видео», нейтральные описания и серьёзное оформление без обозначения пародии в DOM. Диагностические пределы временно видны по запросу пользователя; актуальная модель множителей описана в design/FPS.md. Локальный Roboto Condensed (OFL) и палитра описаны в [design/VIDEO.md](design/VIDEO.md).


## Центральное окно и применение параметров

`studyView.ts` содержит один диалог постоянного размера, вкладки «Звук»/«Видео», фон, закрытие, возврат фокуса и навигацию вкладок стрелками. При открытии настроек сцена не ставится на паузу: это позволяет оценивать живой FPS. Кнопка паузы сцены сохраняет прежнее действие.

`graphicsPanel.ts` хранит отдельно форму и применённые параметры, включая реальное качество сцены. Рендер получает только применённый снимок. Редактирование, F8, сброс, смена вкладки и закрытие не применяют видео. Кнопка справа под описанием атомарно принимает значения; изменение реального качества отправляется в main через video-quality-change и перезапускает замер. Звук меняется сразу, независимо от формы видео. ContactAudio направляет все источники через общий GainNode, регулятор 0–100% управляет им; пауза и выключение заглушают общий выход.
